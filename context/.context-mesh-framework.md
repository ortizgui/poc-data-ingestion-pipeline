# Context Mesh Framework

## Overview

Context Mesh keeps project knowledge close to the code and separated by purpose so AI agents and humans can work from shared context.

The framework has three phases:

1. Intent: document what exists or what should exist, why it matters, and how success is recognized.
2. Build: implement from approved intent and accepted decisions, following documented patterns.
3. Learn: update context after changes so future work starts from the current truth.

## File Type Separation

Feature files describe WHAT and WHY.

- Location: `context/intent/feature-*.md`
- Include user or business value, functional behavior, and acceptance criteria.
- Do not include implementation details, library names, file paths, code examples, or architecture choices.
- Link to decisions and patterns instead of repeating technical detail.

Decision files describe technical HOW.

- Location: `context/decisions/*.md`
- Include architecture choices, libraries, services, data formats, approaches, rationale, alternatives, and outcomes.
- Use accepted decisions as constraints during build work.

Knowledge files describe HOW TO IMPLEMENT.

- Location: `context/knowledge/patterns/*.md`
- Include reusable code patterns, examples from the codebase, conventions, and implementation guidance.
- Use patterns when adding or changing code.

Agent files describe WHO/WHEN.

- Location: `context/agents/*.md`
- Include specialist agent instructions, execution roles, and delegation rules when the project needs them.

Anti-pattern files describe WHAT TO AVOID.

- Location: `context/knowledge/anti-patterns/*.md`
- Include practices known to cause defects, cost, complexity, or drift.

## Plan, Approve, Execute Pattern

Plan, Approve, Execute is mandatory for non-trivial changes.

1. Plan: load relevant context, identify impacted features, decisions, and patterns, then propose the smallest safe change.
2. Approve: wait for explicit approval when the change is architectural, risky, expensive, or conflicts with existing context.
3. Execute: implement the approved change, verify it, and update Context Mesh.

For small documentation-only updates or straightforward bug fixes, approval can be implicit when the user directly requested the edit.

## When To Create Files

Create a feature file when a distinct user/business capability exists or is added.

Create a decision file when a technical choice is made or discovered, including service selection, library selection, architecture style, data model, storage layout, orchestration approach, testing approach, or operational tradeoff.

Create a pattern file when code shows a repeatable implementation convention or reusable approach.

Create a changelog entry whenever behavior, context, decisions, or patterns change.

## When Not To Create Files

Do not create a feature file for a purely technical helper with no standalone user/business value.

Do not create a decision file for a trivial implementation detail that can be understood directly from code.

Do not create a pattern file for one-off code that should not be repeated.

Do not duplicate the same knowledge across file types. Link instead.

## Bidirectional Links

Use links to connect context without mixing concerns.

- Feature files link to related decision files and pattern files.
- Decision files link back to related feature files and any supporting patterns.
- Pattern files link to related decision files and feature files.
- Use markdown links with relative paths.
- Update links when files are renamed or moved.

## Status Section Requirements

Every Context Mesh file must include a Status section.

Feature status includes created date, phase, current status, and whether it is implemented.

Decision status includes created date, phase, accepted/proposed/superseded status, and implementation note.

Pattern status includes created date and active/deprecated status.

Project intent includes created date, phase, active status, and generation note.

## Definition Of Done

Before completing build work:

- Relevant context was loaded.
- Feature intent remains accurate.
- Required decision files exist before implementation.
- Code follows documented patterns.
- Tests or verification ran, or the reason for skipping is documented.
- Context files reflect the final state.
- Changelog is updated.
